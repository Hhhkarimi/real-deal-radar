# ربات کانال تخفیف واقعی · Real Deal Radar

ربات متن‌باز انتشار خودکار در کانال تلگرام: هر ۶ ساعت یک پست جمع‌بندی‌شده از تخفیف‌های غیرسوپرمارکتی می‌سازد. فاصلهٔ بررسی همچنان در اختیار مدیر کانال است. هر پست شامل قیمت، صرفه‌جویی نسبت به بازار و لینک خرید است؛ گزارش کامل شواهد در فایل HTML/JSON باقی می‌ماند.

**وضعیت نسخهٔ 0.4:** اتصال مستقیم دیجی‌کالا با نگهداری کوکی سایت و endpoint فعلی شگفت‌انگیزها پیاده شده و دریافت زنده آزمایش شده است. کشف خودکار فروشنده‌های بازار از ترب انجام می‌شود؛ شاهد معتبر از صفحهٔ خود فروشگاه استخراج می‌شود. این اتصال‌ها API رسمیِ قراردادی نیستند و با تغییر سایت ممکن است نیاز به اصلاح داشته باشند. تطبیق دقیق داده‌های ساختاریافته، دامنهٔ پوشش را محدود می‌کند؛ نبود شواهد با تخفیف واقعی جایگزین نمی‌شود.

## اجرای سریع نمونهٔ آفلاین

Python 3.11 یا جدیدتر:

```bash
python -m venv .venv
source .venv/bin/activate
pip install .
python examples/refresh_demo.py
dealradar demo --config examples/demo.toml
python -m http.server 8080 --directory demo-output --bind 127.0.0.1
```

صفحهٔ `http://127.0.0.1:8080` را باز کنید. دادهٔ نمونه ساختگی است و گزارش با برچسب روشن «دادهٔ نمایشی» تولید می‌شود. در Windows به‌جای دستور source، `.venv\Scripts\activate` را اجرا کنید. خروجی‌ها: `index.html`، `latest.md` و `latest.json`.

## انتخاب ساعت بررسی

در `config.toml` عدد مورد نظر را بنویسید:

```toml
interval_hours = 3
```

۱، ۳، ۶، ۱۲، ۲۴ یا هر عدد مثبت دیگر، حتی `0.5` برای نیم‌ساعت، پذیرفته می‌شود. سپس:

```bash
dealradar check --config config.toml
dealradar watch --config config.toml
```

اولین بررسی بلافاصله انجام می‌شود. برنامه هر ۱۰ ثانیه تنظیمات را دوباره می‌خواند؛ فاصله از **شروع بررسی قبلی** محاسبه می‌شود. با تغییر عدد، برنامه را لازم نیست دوباره اجرا کنید. اگر دریافت داده طولانی‌تر از فاصله باشد، اجراها هم‌زمان نمی‌شوند و بررسی بعدی پس از پایان قبلی انجام می‌شود. حداقل عملی را متناسب با محدودیت منابع انتخاب کنید.

برای تغییر موقت در خط فرمان:

```bash
dealradar watch --config config.toml --interval-hours 12
```

این override تا پایان آن پردازش بر تنظیم فایل اولویت دارد. برای یک گزارش بدون زمان‌بندی: `dealradar run --config config.toml`.

## دادهٔ واقعی و اتصال منابع

### دیجی‌کالا

با `[digikala] enabled = true`، تعدادی صفحه از endpoint عمومی پیشنهادهای شگفت‌انگیز خوانده می‌شود. محدودیت نرخ، تغییر قالب داده یا نبود طبقه‌بندی معتبر، به وضعیت خطا/تأییدنشده منجر می‌شود. آداپتور با دسترسی مستقیم زنده آزمایش شده است. نبود طبقه‌بندی صریح با مسیر دسته‌بندی معتبر بررسی می‌شود؛ دستهٔ ناشناخته محافظه‌کارانه حذف می‌شود. سلامت اتصال در runner گیتهاب نیز باید با پیش‌نمایش بررسی شود.

برای نامزدهای دریافت‌شده، `output/latest.json` شناسه‌های `product_key`، `variant_key` و `warranty_key` را نشان می‌دهد. در مسیر پیش‌فرض کشف بازار خودکار است. اگر از JSON feed یا نگاشت دستی استفاده می‌کنید، دو منبع مستقل را به همین شناسه‌ها وصل کنید و اتصال را بازبینی کنید؛ نام مشابه کافی نیست.

### روش ۱: JSON feed محلی یا HTTPS

قالب کامل در `examples/market.json` موجود است. در تنظیمات:

```toml
[feeds]
candidates = []
market = ["my-market.json", "https://your-provider.example/market.json"]
```

برای منبع جایگزین نامزدها، `[digikala] enabled = false` و `candidates = ["my-candidates.json"]` بگذارید. آداپتورهای دیگر کافی است همین قرارداد را تولید کنند:

| فیلد | معنا |
|---|---|
| `product_key` | هویت دقیق مدل؛ برای دیجی‌کالا `dkp:12345` |
| `variant_key` | رنگ، ظرفیت، اندازه و تعداد در بسته |
| `warranty_key` | گارانتی همسان؛ تفاوت آن مانع مقایسه می‌شود |
| `seller_id` | هویت واقعی فروشنده؛ چند دامنهٔ یک فروشنده یک شاهد است |
| `price_toman` | قیمت نقدی قابل خرید، عدد به تومان؛ مبلغ قسط قابل قبول نیست |
| `shipping_toman` | مبلغ ارسال برای شرایط یکسان؛ `null` اگر مشخص نیست |
| `observed_at` | زمان واقعی مشاهده با timezone؛ برای تازه جلوه دادن داده بازنویسی نکنید |
| `in_stock` | موجودی تأییدشده، boolean |
| `supermarket` | طبقه‌بندی سوپرمارکتی، boolean |
| `category`، `title`، `url` | دسته، عنوان و صفحهٔ HTTPS کالا |
| `discount_percent` | درصد درج‌شده؛ در نامزدها لازم است، در بازار می‌تواند صفر باشد |
| `expires_at` | اختیاری؛ پایان پیشنهاد با timezone |

پیش‌فرض حداکثر سن شواهد ۶ ساعت است؛ مستقل از فاصلهٔ اجرای کاربر. با بررسی روزانه نیز شواهدِ قیمتِ زمان اجرا باید تازه باشد. صحت هویت و قیمت feed بر عهدهٔ فراهم‌کنندهٔ داده است؛ دو feed کپی‌شده از یک فروشنده، دو شاهد مستقل نیستند.

### روش ۲: صفحات فروشگاه با schema.org JSON-LD

بخش زیر را در سطح اصلی فایل تنظیمات، **قبل از** `[digikala]` و `[feeds]` اضافه کنید؛ برای هر فروشنده یک بلوک مستقل:

```toml
[[market_pages]]
product_key = "dkp:12345"
title = "نام دقیق کالا"
url = "https://shop.example/products/exact-product"
seller_id = "merchant:shop-owner-1"
expected_sku = "EXACT-SHOP-SKU"
variant_key = "color:1|size:none"
warranty_key = "عنوان دقیق گارانتی"
category = "هدفون"
supermarket = false
# shipping_toman = 50000  # فقط اگر مبلغ واقعی برای شرایط یکسان مشخص است
```

خواننده فقط Product دارای SKU منطبق و یک Offer مشخص را قبول می‌کند. `InStock` لازم است؛ AggregateOffer، قیمت بدون ارز، چند Offer مبهم یا SKU متفاوت پذیرفته نمی‌شوند. `IRR` بر ۱۰ تقسیم می‌شود؛ `IRT` تومان است. فروشگاه‌های بدون این داده نیاز به آداپتور اختصاصی دارند. این روش CAPTCHA یا محدودیت دسترسی را دور نمی‌زند.

## دریافت واقعی و خودکار قیمت بازار

در تنظیمات پیش‌فرض، `[digikala]` و `[torob]` فعال‌اند. توکن یا API key قیمت لازم نیست. دیجی‌کالا با session کوکی HTTP استاندارد خوانده می‌شود؛ کوکی فقط در حافظه می‌ماند. فهرست شگفت‌انگیزها از `/v1/incredible-offers/products/` و جزئیات نهایی از `/v2/product/{id}/` دریافت می‌شوند. گارانتی از `title_fa`، رنگ/سایز از نسخهٔ واقعی و غیرسوپرمارکتی بودن از طبقه‌بندی مثبت سایت خوانده می‌شود. دستهٔ نامعلوم، موجودی نامعلوم و قیمت مخصوص عضویت کنار گذاشته می‌شوند.

ترب با نام کالا جست‌وجو می‌شود، فروشنده‌های دارای موجودی کشف می‌شوند و لینک آن‌ها تا صفحهٔ فروشگاه دنبال می‌شود. قیمت تجمیعی ترب به تنهایی «شاهد تأییدشده» نیست. برای پذیرفتن شاهد، صفحهٔ فروشگاه باید یک Product با نام دقیق (پس از یکسان‌سازی ی/ک، ارقام و علائم)، یا با کد کامل مدل در نام محصول یا MPN و برند همسان، رنگ، سایز و گارانتی یکسان و یک Offer با قیمت، ارز و موجودی صریح داشته باشد. برای مسیر شناسهٔ مدل، ظرفیت، تعداد بسته و پسوند نسخه نیز باید یکسان باشند. مشخصات جدول اختصاصی WooCommerce نیز برای صفحهٔ دارای تنها یک Product خوانده می‌شوند. نام مشابه، گارانتیِ ذکرشده در پاورقی عمومی و قیمت AggregateOffer پذیرفته نمی‌شوند. این روش دقت را بر پوشش ترجیح می‌دهد؛ بسیاری از فروشگاه‌ها این اطلاعات را در JSON-LD منتشر نمی‌کنند و کنار گذاشته می‌شوند.

برای هر نوبت، حداکثر ۴۰ نامزد واجد شرایط، ۲ نتیجهٔ جست‌وجو و ۴ فروشنده از هر نتیجه بررسی می‌شوند. سقف زمان ترب پیش‌فرض ۴۸۰ ثانیه است؛ این حدود در بخش `[torob]` تغییر می‌کنند. گزارش تعداد کالاهایی که واقعاً وارد جست‌وجوی بازار شدند را نشان می‌دهد. فایل `output/market-discovery.json` لینک نتایج، قیمت تجمیعی صرفاً برای بررسی و علت رد فروشنده‌ها را نگه می‌دارد. دریافت صفحهٔ دیجی‌کالا به معنی تأیید قیمت زیر بازار نیست.

قبل از انتشار پیشنهاد تأییدشده، قیمت دیجی‌کالا و شاهدهای مستقیم فروشگاه دوباره خوانده می‌شوند. نوبتی که فروشندهٔ قابل‌تطبیق کافی ندارد، وضعیت نبود پیشنهاد معتبر منتشر می‌کند. هیچ تضمینی برای یافتن روزانهٔ ۲۰ تخفیف واقعی وجود ندارد. فایل `LIVE-VALIDATION.md` نتیجهٔ آزمایش واقعی این نسخه را ثبت می‌کند.

## قواعد تأیید

- کالا غیرسوپرمارکتی، موجود و شواهد تازه باشد.
- محصول، نسخه و گارانتی دقیقاً همسان باشند.
- حداقل دو فروشندهٔ مستقل و دامنه‌های جدا از صفحهٔ نامزد داشته باشیم.
- درصد درج‌شده حداقل ۲۰٪ و صرفه‌جویی نسبت به **کمترین قیمت معتبر پیدا‌شده** حداقل ۱۵٪ باشد؛ هر دو قابل تنظیم هستند.
- قیمت نامزد پیش از انتشار دوباره خوانده شود؛ تغییر نسخه یا شکست دریافت، تأیید را لغو می‌کند.
- اگر ارسال هر منبع نامعلوم باشد، همهٔ قیمت‌ها بدون ارسال مقایسه می‌شوند و برچسب آن در گزارش می‌آید.
- حداکثر ۲۰ پیشنهاد؛ اگر کمتر بود، فهرست با کالای ضعیف پر نمی‌شود.

تاریخچهٔ ۳۰روزه از زمان شروع استفاده جمع می‌شود. گزارش «کمترین قیمت ثبت‌شده» را نشان می‌دهد؛ ادعای کشف قطعی قیمت‌سازی یا ارزان‌ترین بودن در کل بازار ندارد. بررسی همهٔ فروشندگان اینترنت ممکن نیست. جمع‌آوری نامزدها محدود به صفحات تنظیم‌شده است.

## راه‌اندازی ربات کانال تلگرام

۱. در تلگرام از [BotFather](https://t.me/BotFather) با دستور `/newbot` ربات بسازید و توکن آن را دریافت کنید.

۲. ربات را به کانال اضافه کنید و به آن دسترسی مدیر با مجوز **Post Messages / ارسال پیام** بدهید.

۳. برای کانال عمومی از `@your_channel` استفاده کنید. برای کانال خصوصی، شناسهٔ عددی دقیق کانال معمولاً با `-100` شروع می‌شود؛ آن را از یک update متعلق به همان کانال یا ابزار مورد اعتماد خودتان دریافت کنید. شناسه را از لینک دعوت حدس نزنید.

۴. در روش Python، متغیرهای محیطی را تنظیم کنید:

```bash
export TELEGRAM_BOT_TOKEN='YOUR_TOKEN'
export TELEGRAM_CHAT_ID='@your_channel'
dealradar watch --config config.toml
```

در Windows از متغیرهای محیطی PowerShell استفاده کنید:

```powershell
$env:TELEGRAM_BOT_TOKEN = 'YOUR_TOKEN'
$env:TELEGRAM_CHAT_ID = '@your_channel'
dealradar watch --config config.toml
```

پیش‌فرض فایل `config.toml`، `interval_hours = 6` و `[telegram] enabled = true` است. توکن واقعی را در مخزن عمومی ذخیره نکنید.

### رفتار انتشار

- اولین بررسی هنگام اجرای worker انجام می‌شود؛ سپس هر ۶ ساعت یک نوبت بررسی و انتشار.
- در هر نوبت **یک پست** منتشر می‌شود؛ برای هر کالا پیام جدا ارسال نمی‌شود.
- حتی اگر قیمت‌ها تغییر نکرده باشند، نوبت بعدی گزارش جدید خود را منتشر می‌کند.
- اگر پیشنهاد معتبر نداریم، پست صریحاً همین نتیجه را اعلام می‌کند.
- اگر دریافت تمام داده شکست بخورد، پست «دریافت داده ناموفق بود» منتشر می‌شود؛ این حالت با نبود تخفیف معتبر متفاوت است.
- ارسال موفق با شناسهٔ پیام در SQLite ثبت می‌شود. ارسال مجدد همان بازهٔ زمانی بعد از restart حذف می‌شود؛ جدول قبلی اعلان‌های کالایی دیگر در انتشار دخالت ندارد.
- محدودیت متن تلگرام رعایت می‌شود: قالب نمونه با ۲۰ کالا در یک پست جا می‌گیرد. اگر متن بیشتر شود، تعدادی از پیشنهادها به گزارش کامل ارجاع داده می‌شوند.
- برای پاسخ 429 تلگرام تا سه تلاش با تأخیر محدود انجام می‌شود. برای timeout مبهم، retry فوری انجام نمی‌شود؛ چون ممکن است تلگرام پیام را دریافت کرده باشد. Bot API تضمین exactly-once ندارد؛ پس بعد از شکست مبهم و restart، احتمال پیام تکراری کاملاً قابل حذف نیست.
- فاصله از شروع بررسی قبلی محاسبه می‌شود؛ برای ساعت ثابتِ تقویمی مثل ۰۰/۰۶/۱۲/۱۸ طراحی نشده است. برای هر نصب یک worker اجرا کنید.

برای افزودن لینک گزارش کامل به انتهای پست، در بخش `[telegram]` بنویسید:

```toml
report_url = "https://your-site.example/deals/"
```

این گزینه خودبه‌خود سایت را میزبانی نمی‌کند؛ آدرس باید گزارش واقعاً منتشرشده باشد.

### پیش‌نمایش بدون ارسال

```bash
dealradar preview --config config.toml
```

این دستور داده‌های واقعی پیکربندی‌شده را بررسی می‌کند و فایل `output/channel-post.html` می‌سازد؛ هیچ پیامی ارسال نمی‌کند. برای پیش‌نمایش ساختگی و بدون شبکه:

```bash
python examples/refresh_demo.py
dealradar demo --config examples/demo.toml
```

فایل `demo-output/channel-post.html` را باز کنید. حالت demo با برچسب مشخص، هیچ‌گاه به کانال پیام نمی‌فرستد.

توکن را در کد، feed یا فایل عمومی نگذارید. فایل `.env` در gitignore قرار دارد؛ برای Docker از `.env.example` کپی بگیرید. این ربات منتشرکنندهٔ کانال است؛ منوی گفت‌وگویی، دریافت دستورات از اعضا یا webhook نیاز ندارد.

مرجع رسمی Telegram Bot API: https://core.telegram.org/bots/api#sendmessage

## Docker

```bash
cp .env.example .env
# در Linux مقدار RADAR_UID و RADAR_GID را برابر id -u و id -g قرار دهید.
docker compose up --build -d
docker compose logs -f
```

فایل تنظیمات و خروجی‌ها در پوشهٔ پروژه mount می‌شوند. تغییر `interval_hours` بدون restart اعمال می‌شود. برای توقف: `docker compose down`. خود ایمیج با کاربر غیر root اجرا می‌شود؛ compose از UID/GID کاربر شما برای نوشتن خروجی استفاده می‌کند.

## انتشار خودکار کانال با GitHub Actions

برای این روش سرور شخصی لازم نیست. فایل‌های داخل پوشهٔ پروژه را در ریشهٔ مخزن `real-deal-radar` روی شاخهٔ پیش‌فرض قرار دهید؛ پوشهٔ مخفی `.github` هم باید آپلود شود. بارگذاری خود فایل ZIP باعث اجرا نمی‌شود.

1. در BotFather ربات بسازید و آن را با مجوز **Post Messages** مدیر کانال کنید.
2. در مخزن به **Settings → Secrets and variables → Actions → New repository secret** بروید و `TELEGRAM_BOT_TOKEN` و `TELEGRAM_CHAT_ID` را ثبت کنید. شناسهٔ کانال عمومی مانند `@your_channel` یا شناسهٔ عددی کانال خصوصی است.
3. دریافت مستقیم دیجی‌کالا و کشف بازار از ترب در تنظیمات پیش‌فرض فعال است. در صورت داشتن منبع اختصاصی، Secret اختیاری `MARKET_FEED_URL` (جایگزین ترب) یا `CANDIDATE_FEED_URL` (جایگزین دیجی‌کالا) را مطابق قالب JSON نمونه تنظیم کنید. فایل نمونه دادهٔ ساختگی است و برای انتشار واقعی مناسب نیست.
4. در **Actions → Telegram channel report → Run workflow** ابتدا گزینهٔ **Preview only** را روشن بگذارید. فایل گزارش در Artifacts همان اجرا قابل دریافت است. سپس اجرای دستی را با خاموش کردن آن گزینه انجام دهید تا پست منتشر شود.
5. اجرای زمان‌بندی‌شده پس از قرار گرفتن workflow روی شاخهٔ پیش‌فرض، با Actions فعال، هر ۶ ساعت انجام می‌شود. پیش‌نمایش دستی زمان‌بندی را متوقف نمی‌کند؛ تنظیم منابع و Secrets را پیش از فعال کردن Actions کامل کنید.

زمان‌ها با cron برابر `17 */6 * * *` تنظیم شده‌اند؛ در تهران حدود ۰۳:۴۷، ۰۹:۴۷، ۱۵:۴۷ و ۲۱:۴۷. زمان اجرا تضمین دقیق ندارد و ممکن است عقب بیفتد یا حذف شود. در مخزن عمومی بدون فعالیت، GitHub ممکن است پس از ۶۰ روز زمان‌بندی را غیرفعال کند. مرجع: [GitHub scheduled workflows](https://docs.github.com/en/actions/reference/workflows-and-actions/events-that-trigger-workflows#schedule).

برای تغییر فاصله، هم `interval_hours` در `config.toml` و هم cron در `.github/workflows/channel.yml` را تغییر دهید؛ برای ۳ ساعت، `interval_hours = 3` و `17 */3 * * *`. cron برای فاصله‌های دلخواه اعشاری مناسب نیست؛ worker محلی از آن‌ها پشتیبانی می‌کند.

تاریخچهٔ قیمت و ارسال با GitHub Cache بین اجراها منتقل می‌شود؛ حذف یا انقضای cache تاریخچه را از دسترس خارج می‌کند، پس ذخیره‌سازی دائمی تضمین نمی‌شود. اجراهای این workflow هم‌زمان نمی‌شوند. یک پست در هر بازهٔ UTC ارسال می‌شود و کمی تأخیر اجرای قبلی باعث حذف بازهٔ بعدی نمی‌شود. در نبود ۲۰ پیشنهاد معتبر، فقط تعداد تأییدشده گزارش می‌شود؛ بدون شاهد بازار، وضعیت نبود پیشنهاد معتبر منتشر می‌شود.

هر مخزن/نصب یک کانال و تنظیم مستقل دارد. کاربران می‌توانند مخزن را Fork کنند و Secrets خودشان را تنظیم کنند. این بسته ربات چندکاربره با فرمان‌های تلگرامی نیست.

## توسعه و آزمون

```bash
python -m unittest discover -s tests -v
```

آزمون‌ها پوشش می‌دهند: مقایسه با پایین‌ترین قیمت، جلوگیری از شاهد تکراری، نسخه/گارانتی، شواهد قدیمی/آینده/منقضی، ارسال، دادهٔ نامعتبر، ذخیرهٔ تاریخچه، تغییر زمان‌بندی بدون restart، تبدیل ریال، SKU دقیق، تولید گزارش و escape HTML، و تولید یک پست کانالی، محدودیت متن، جلوگیری از انتشار تکراری پس از restart، خطای نرخ و شکست ارسال. تست CI برای Python 3.11، 3.12 و 3.13 آماده است.

محدودیت فعلی: یک worker برای هر فایل پایگاه داده اجرا کنید؛ چند پردازش هم‌زمان برای یک نصب پشتیبانی نمی‌شود. در روش worker، عمر برنامه به روشن بودن دستگاه/سرور بستگی دارد. ابزار دارای retry محدود و timeout است؛ دریافت ناموفق در گزارش پنهان نمی‌شود. worker به سرور یا دستگاه همیشه روشن نیاز دارد؛ روش GitHub Actions روی runner گیتهاب اجرا می‌شود. در هر دو روش اتصال قابل دسترس به Telegram Bot API لازم است.

نسخهٔ 0.4.1: انتخاب نامزدها بین دسته‌ها تقسیم می‌شود و مدل‌های دارای شناسهٔ قابل‌تطبیق اولویت دارند؛ بنابراین اولین کالاهای یک دسته کل سهمیه را مصرف نمی‌کنند. علت‌های شکست جست‌وجو و تطبیق در لاگ Actions به‌صورت شمارش‌های فاقد مقادیر Secrets ثبت می‌شوند. این تغییر تضمین یافتن ۲۰ پیشنهاد معتبر نیست.

نسخهٔ 0.4.2: فیلد `installment.providers` ترب گزینهٔ پرداخت اقساطی است و دیگر باعث حذف فروشندهٔ نقدی نمی‌شود. مبلغ مورد مقایسه همچنان از Offer واقعی فروشگاه خوانده می‌شود؛ مبلغ قسط به جای قیمت کالا استفاده نمی‌شود. ردیف‌های تکراری یک فروشگاه پیش از تخصیص سهمیه حذف می‌شوند.
