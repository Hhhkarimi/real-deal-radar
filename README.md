# ربات کانال تخفیف واقعی · Real Deal Radar

ربات متن‌باز شکار فرصت خرید: هر ۱۵ دقیقه پیشنهادهای دیجی‌کالا را پایش می‌کند؛ شکار ویژه را پس از تشخیص و بازبینی، بدون انتظار برای گزارش بعدی اعلام می‌کند و هر ۱۲ ساعت حداکثر ۳ پیشنهاد تأییدشده و متنوع می‌فرستد. اگر پیشنهاد مناسبی پیدا نشود، سکوت می‌کند. گزارش کامل شواهد و دلایل رد در فایل HTML/JSON باقی می‌ماند.

## حالت پیش‌فرض جدید: شکارگر دارای حافظه

| رفتار | پیش‌فرض |
|---|---|
| پایش | هر ۱۵ دقیقه؛ اولویت با کالای تازه، افت قیمت و سپس مواردی است که مدت بیشتری بررسی نشده‌اند |
| شکار ویژه | حداقل ۲۵٪ و ۲۵۰ هزار تومان پایین‌تر از کمترین پیشنهاد همسانِ معتبر بررسی‌شده |
| گلچین ۱۲ساعته | حداکثر ۳ کالا؛ حداقل ۱۵٪ و ۱۰۰ هزار تومان صرفه‌جویی واقعی |
| تأیید بازار | حداقل ۳ فروشنده و دامنهٔ مستقل؛ مدل، رنگ/سایز، گارانتی و وضعیت کالا باید همسان باشند |
| تازگی شواهد | حداکثر ۲۰ دقیقه؛ قیمت و موجودی نامزدها پیش از ارسال دوباره بررسی می‌شود |
| تنوع | در هر گلچین حداکثر یک کالا از هر نوع؛ هیچ کالایی صرفاً برای پرکردن تعداد اضافه نمی‌شود |
| کنترل تکرار | همان کالا، حتی با تغییر رنگ یا قیمت جزئی، تا ۷ روز تکرار نمی‌شود |
| استثنای تکرار | فقط شکار ویژه با حداقل ۱۰٪ افت بیشتر نسبت به قیمت ارسال‌شده و گذشت حداقل ۶ ساعت |
| سقف شکار ویژه | حداکثر ۲ کالا در هر نوبت و ۴ کالا در هر روز به وقت تهران |

درصد تخفیف تبلیغاتی شرط لازم شکار نیست؛ اختلاف قیمت واقعی با بازار ملاک است. پیشنهاد تأییدنشده و فهرست پرفروش‌ها وارد اعلان‌های این حالت نمی‌شوند. شواهد ناقص، گارانتی مبهم، قیمت نامعتبر، انقضا و عدم پاسخ‌گویی منبع، باعث سکوت یا ثبت خطا در گزارش می‌شوند.

این یک عامل دارای چرخهٔ پایش، راستی‌آزمایی، انتخاب و حافظه است؛ تصمیم قیمت به مدل زبانی و حدس آن وابسته نیست. «ارزان‌ترین قیمت کل اینترنت» قابل تضمین نیست؛ متن اعلان صریحاً کمترین قیمت **منابع همسان بررسی‌شده** را می‌گوید و هزینهٔ ارسال نامشخص را از مقایسه جدا می‌کند. نمودار قیمت ثبت‌شده نیز فقط تاریخچهٔ مشاهدات خود ربات است.

تمام حدود در بخش `[agent]` فایل `config.toml` قابل تغییرند. `interval_hours` فاصلهٔ پایش است و `agent.digest_hours` فاصلهٔ گزارش؛ کم‌کردن اولی باعث بیشترشدن گزارش‌های دوره‌ای نمی‌شود. با `agent.enabled = false` مسیر گزارش قدیمی فعال می‌شود؛ بخش‌های ویترین و پرفروش‌ها در تنظیم پیش‌فرض خاموش‌اند. توضیحات بعدی دربارهٔ حالت قدیمی فقط در صورت فعال‌کردن همان بخش‌ها کاربرد دارند.

### اجرا و فعال‌سازی

پس از ادغام تغییرات در شاخهٔ اصلی، workflow شکارگر هر ۱۵ دقیقه اجرا می‌شود و از همان `TELEGRAM_BOT_TOKEN` و `TELEGRAM_CHAT_ID` موجود در Actions secrets استفاده می‌کند. اجرای دستی نیز کنترل تکرار و فاصلهٔ ۱۲ساعته را دور نمی‌زند. گزینهٔ `dry_run` پیش‌نمایش می‌سازد و هیچ پیام یا حافظهٔ بیرونی را تغییر نمی‌دهد.

حافظهٔ SQLite روی شاخهٔ مستقل `radar-state` نگه‌داری می‌شود؛ workflow برای نوشتن این فایل به `contents: write` نیاز دارد. کش قدیمی فقط برای انتقال سابقه یا بازیابی ذخیرهٔ جدیدتر پس از خطا استفاده می‌شود. خطای خواندن یا خرابی حافظهٔ موجود، انتشار را متوقف می‌کند. توکن تلگرام و شناسهٔ خام کانال در پایگاه داده ذخیره نمی‌شوند. برای timeout مبهم تلگرام، کالا تا پایان دورهٔ جلوگیری از تکرار کنار گذاشته می‌شود؛ خطا و تعداد ارسال تأییدشده در گزارش قابل بررسی است.

زمان‌بندی [GitHub Actions ممکن است تأخیر داشته باشد یا در بار بالا حذف شود](https://docs.github.com/en/actions/reference/workflows-and-actions/events-that-trigger-workflows#schedule)؛ فاصلهٔ ۱۵ دقیقه یک برنامهٔ پایش است و تضمین اعلان لحظه‌ای نیست. برای پایش کوتاه‌تر روی سرور دائمی از Docker Compose موجود یا دستور زیر استفاده کنید؛ نمونهٔ `0.083333` تقریباً ۵ دقیقه است. هر کانال باید فقط یک worker فعال با حافظهٔ مشترک پایدار داشته باشد.

```bash
dealradar check --config config.toml
dealradar preview --config config.toml
dealradar watch --config config.toml --interval-hours 0.083333
```

پوشش کشف محدود به صفحات تنظیم‌شدهٔ پیشنهادهای دیجی‌کالا و بودجهٔ مقایسهٔ ترب است. هر نوبت حداکثر ۲۴ نامزد تا سقف ۶ دقیقه برای مقایسه انتخاب می‌شوند؛ حافظه اولویت بررسی را بین نامزدها می‌چرخاند و کالاهای تازه یا دارای افت قیمت را جلو می‌آورد. برای همین، همهٔ کالاهای جهان یا همهٔ قیمت‌های همان لحظه پوشش داده نمی‌شوند. نسخهٔ تازه را ابتدا با `dry_run` در runner واقعی بررسی کنید؛ اتصال‌های فروشگاه‌ها رسمی و تضمین‌شده نیستند.

**وضعیت نسخهٔ 0.4:** اتصال مستقیم دیجی‌کالا با نگهداری کوکی سایت و endpoint فعلی شگفت‌انگیزها پیاده شده و دریافت زنده آزمایش شده است. کشف خودکار فروشنده‌های بازار از ترب انجام می‌شود؛ شاهد معتبر از صفحهٔ خود فروشگاه استخراج می‌شود. این اتصال‌ها API رسمیِ قراردادی نیستند و با تغییر سایت ممکن است نیاز به اصلاح داشته باشند. تطبیق دقیق داده‌های ساختاریافته، دامنهٔ پوشش را محدود می‌کند؛ نبود شواهد با تخفیف واقعی جایگزین نمی‌شود.

## اجرای سریع نمونهٔ آفلاین

Python 3.11 یا جدیدتر:

```bash
python -m venv .venv
source .venv/bin/activate
pip install .
python examples/refresh_demo.py
dealradar demo --config examples/demo.toml
python -m http.server 8080 --directory demo-output --bind 127.0.0.1
```

صفحهٔ `http://127.0.0.1:8080` را باز کنید. دادهٔ نمونه ساختگی است و گزارش با برچسب روشن «دادهٔ نمایشی» تولید می‌شود. در Windows به‌جای دستور source، `.venv\Scripts\activate` را اجرا کنید. خروجی‌ها: `index.html`، `latest.md` و `latest.json`.

## انتخاب ساعت بررسی

در `config.toml` عدد مورد نظر را بنویسید:

```toml
interval_hours = 3
```

۱، ۳، ۶، ۱۲، ۲۴ یا هر عدد مثبت دیگر، حتی `0.5` برای نیم‌ساعت، پذیرفته می‌شود. سپس:

```bash
dealradar check --config config.toml
dealradar watch --config config.toml
```

اولین بررسی بلافاصله انجام می‌شود. برنامه هر ۱۰ ثانیه تنظیمات را دوباره می‌خواند؛ فاصله از **شروع بررسی قبلی** محاسبه می‌شود. با تغییر عدد، برنامه را لازم نیست دوباره اجرا کنید. اگر دریافت داده طولانی‌تر از فاصله باشد، اجراها هم‌زمان نمی‌شوند و بررسی بعدی پس از پایان قبلی انجام می‌شود. حداقل عملی را متناسب با محدودیت منابع انتخاب کنید.

برای تغییر موقت در خط فرمان:

```bash
dealradar watch --config config.toml --interval-hours 12
```

این override تا پایان آن پردازش بر تنظیم فایل اولویت دارد. برای یک گزارش بدون زمان‌بندی: `dealradar run --config config.toml`.

## دادهٔ واقعی و اتصال منابع

### دیجی‌کالا

با `[digikala] enabled = true`، تعدادی صفحه از endpoint عمومی پیشنهادهای شگفت‌انگیز خوانده می‌شود. محدودیت نرخ، تغییر قالب داده یا نبود طبقه‌بندی معتبر، به وضعیت خطا/تأییدنشده منجر می‌شود. آداپتور با دسترسی مستقیم زنده آزمایش شده است. نبود طبقه‌بندی صریح با مسیر دسته‌بندی معتبر بررسی می‌شود؛ دستهٔ ناشناخته محافظه‌کارانه حذف می‌شود. سلامت اتصال در runner گیتهاب نیز باید با پیش‌نمایش بررسی شود.

برای نامزدهای دریافت‌شده، `output/latest.json` شناسه‌های `product_key`، `variant_key` و `warranty_key` را نشان می‌دهد. در مسیر پیش‌فرض کشف بازار خودکار است. اگر از JSON feed یا نگاشت دستی استفاده می‌کنید، دو منبع مستقل را به همین شناسه‌ها وصل کنید و اتصال را بازبینی کنید؛ نام مشابه کافی نیست.

### روش ۱: JSON feed محلی یا HTTPS

قالب کامل در `examples/market.json` موجود است. در تنظیمات:

```toml
[feeds]
candidates = []
market = ["my-market.json", "https://your-provider.example/market.json"]
```

برای منبع جایگزین نامزدها، `[digikala] enabled = false` و `candidates = ["my-candidates.json"]` بگذارید. آداپتورهای دیگر کافی است همین قرارداد را تولید کنند:

| فیلد | معنا |
|---|---|
| `product_key` | هویت دقیق مدل؛ برای دیجی‌کالا `dkp:12345` |
| `variant_key` | رنگ، ظرفیت، اندازه و تعداد در بسته |
| `warranty_key` | گارانتی همسان؛ تفاوت آن مانع مقایسه می‌شود |
| `seller_id` | هویت واقعی فروشنده؛ چند دامنهٔ یک فروشنده یک شاهد است |
| `price_toman` | قیمت نقدی قابل خرید، عدد به تومان؛ مبلغ قسط قابل قبول نیست |
| `shipping_toman` | مبلغ ارسال برای شرایط یکسان؛ `null` اگر مشخص نیست |
| `observed_at` | زمان واقعی مشاهده با timezone؛ برای تازه جلوه دادن داده بازنویسی نکنید |
| `in_stock` | موجودی تأییدشده، boolean |
| `supermarket` | طبقه‌بندی سوپرمارکتی، boolean |
| `category`، `title`، `url` | دسته، عنوان و صفحهٔ HTTPS کالا |
| `discount_percent` | درصد درج‌شده؛ در نامزدها لازم است، در بازار می‌تواند صفر باشد |
| `expires_at` | اختیاری؛ پایان پیشنهاد با timezone |

پیش‌فرض حداکثر سن شواهد ۶ ساعت است؛ مستقل از فاصلهٔ اجرای کاربر. با بررسی روزانه نیز شواهدِ قیمتِ زمان اجرا باید تازه باشد. صحت هویت و قیمت feed بر عهدهٔ فراهم‌کنندهٔ داده است؛ دو feed کپی‌شده از یک فروشنده، دو شاهد مستقل نیستند.

### روش ۲: صفحات فروشگاه با schema.org JSON-LD

بخش زیر را در سطح اصلی فایل تنظیمات، **قبل از** `[digikala]` و `[feeds]` اضافه کنید؛ برای هر فروشنده یک بلوک مستقل:

```toml
[[market_pages]]
product_key = "dkp:12345"
title = "نام دقیق کالا"
url = "https://shop.example/products/exact-product"
seller_id = "merchant:shop-owner-1"
expected_sku = "EXACT-SHOP-SKU"
variant_key = "color:1|size:none"
warranty_key = "عنوان دقیق گارانتی"
category = "هدفون"
supermarket = false
# shipping_toman = 50000  # فقط اگر مبلغ واقعی برای شرایط یکسان مشخص است
```

خواننده فقط Product دارای SKU منطبق و یک Offer مشخص را قبول می‌کند. `InStock` لازم است؛ AggregateOffer، قیمت بدون ارز، چند Offer مبهم یا SKU متفاوت پذیرفته نمی‌شوند. `IRR` بر ۱۰ تقسیم می‌شود؛ `IRT` تومان است. فروشگاه‌های بدون این داده نیاز به آداپتور اختصاصی دارند. این روش CAPTCHA یا محدودیت دسترسی را دور نمی‌زند.

## دریافت واقعی و خودکار قیمت بازار

در تنظیمات پیش‌فرض، `[digikala]` و `[torob]` فعال‌اند. توکن یا API key قیمت لازم نیست. دیجی‌کالا با session کوکی HTTP استاندارد خوانده می‌شود؛ کوکی فقط در حافظه می‌ماند. فهرست شگفت‌انگیزها از `/v1/incredible-offers/products/` و جزئیات نهایی از `/v2/product/{id}/` دریافت می‌شوند. گارانتی از `title_fa`، رنگ/سایز از نسخهٔ واقعی و غیرسوپرمارکتی بودن از طبقه‌بندی مثبت سایت خوانده می‌شود. دستهٔ نامعلوم، موجودی نامعلوم و قیمت مخصوص عضویت کنار گذاشته می‌شوند.

ترب با نام کالا جست‌وجو می‌شود، فروشنده‌های دارای موجودی کشف می‌شوند و لینک آن‌ها تا صفحهٔ فروشگاه دنبال می‌شود. قیمت تجمیعی ترب به تنهایی «شاهد تأییدشده» نیست. برای پذیرفتن شاهد، صفحهٔ فروشگاه باید یک Product با نام دقیق (پس از یکسان‌سازی ی/ک، ارقام و علائم)، یا با کد کامل مدل در نام محصول یا MPN و برند همسان، رنگ، سایز و گارانتی یکسان و یک Offer با قیمت، ارز و موجودی صریح داشته باشد. برای مسیر شناسهٔ مدل، ظرفیت، تعداد بسته و پسوند نسخه نیز باید یکسان باشند. مشخصات جدول اختصاصی WooCommerce نیز برای صفحهٔ دارای تنها یک Product خوانده می‌شوند. نام مشابه، گارانتیِ ذکرشده در پاورقی عمومی و قیمت AggregateOffer پذیرفته نمی‌شوند. این روش دقت را بر پوشش ترجیح می‌دهد؛ بسیاری از فروشگاه‌ها این اطلاعات را در JSON-LD منتشر نمی‌کنند و کنار گذاشته می‌شوند.

برای هر نوبت، حداکثر ۴۰ نامزد واجد شرایط، ۲ نتیجهٔ جست‌وجو و ۴ فروشنده از هر نتیجه بررسی می‌شوند. سقف زمان ترب پیش‌فرض ۴۸۰ ثانیه است؛ این حدود در بخش `[torob]` تغییر می‌کنند. گزارش تعداد کالاهایی که واقعاً وارد جست‌وجوی بازار شدند را نشان می‌دهد. فایل `output/market-discovery.json` لینک نتایج، قیمت تجمیعی صرفاً برای بررسی و علت رد فروشنده‌ها را نگه می‌دارد. دریافت صفحهٔ دیجی‌کالا به معنی تأیید قیمت زیر بازار نیست.

قبل از انتشار پیشنهاد تأییدشده، قیمت دیجی‌کالا و شاهدهای مستقیم فروشگاه دوباره خوانده می‌شوند. نوبتی که فروشندهٔ قابل‌تطبیق کافی ندارد، وضعیت نبود پیشنهاد معتبر منتشر می‌کند. هیچ تضمینی برای یافتن روزانهٔ ۲۰ تخفیف واقعی وجود ندارد. فایل `LIVE-VALIDATION.md` نتیجهٔ آزمایش واقعی این نسخه را ثبت می‌کند.

## قواعد تأیید

- کالا غیرسوپرمارکتی، موجود و شواهد تازه باشد.
- محصول، نسخه و گارانتی دقیقاً همسان باشند.
- حداقل دو فروشندهٔ مستقل و دامنه‌های جدا از صفحهٔ نامزد داشته باشیم.
- درصد درج‌شده حداقل ۲۰٪ و صرفه‌جویی نسبت به **کمترین قیمت معتبر پیدا‌شده** حداقل ۱۵٪ باشد؛ هر دو قابل تنظیم هستند.
- قیمت نامزد پیش از انتشار دوباره خوانده شود؛ تغییر نسخه یا شکست دریافت، تأیید را لغو می‌کند.
- اگر ارسال هر منبع نامعلوم باشد، همهٔ قیمت‌ها بدون ارسال مقایسه می‌شوند و برچسب آن در گزارش می‌آید.
- حداکثر ۲۰ پیشنهاد؛ اگر کمتر بود، فهرست با کالای ضعیف پر نمی‌شود.

تاریخچهٔ ۳۰روزه از زمان شروع استفاده جمع می‌شود. گزارش «کمترین قیمت ثبت‌شده» را نشان می‌دهد؛ ادعای کشف قطعی قیمت‌سازی یا ارزان‌ترین بودن در کل بازار ندارد. بررسی همهٔ فروشندگان اینترنت ممکن نیست. جمع‌آوری نامزدها محدود به صفحات تنظیم‌شده است.

## راه‌اندازی ربات کانال تلگرام

۱. در تلگرام از [BotFather](https://t.me/BotFather) با دستور `/newbot` ربات بسازید و توکن آن را دریافت کنید.

۲. ربات را به کانال اضافه کنید و به آن دسترسی مدیر با مجوز **Post Messages / ارسال پیام** بدهید.

۳. برای کانال عمومی از `@your_channel` استفاده کنید. برای کانال خصوصی، شناسهٔ عددی دقیق کانال معمولاً با `-100` شروع می‌شود؛ آن را از یک update متعلق به همان کانال یا ابزار مورد اعتماد خودتان دریافت کنید. شناسه را از لینک دعوت حدس نزنید.

۴. در روش Python، متغیرهای محیطی را تنظیم کنید:

```bash
export TELEGRAM_BOT_TOKEN='YOUR_TOKEN'
export TELEGRAM_CHAT_ID='@your_channel'
dealradar watch --config config.toml
```

در Windows از متغیرهای محیطی PowerShell استفاده کنید:

```powershell
$env:TELEGRAM_BOT_TOKEN = 'YOUR_TOKEN'
$env:TELEGRAM_CHAT_ID = '@your_channel'
dealradar watch --config config.toml
```

پیش‌فرض فایل `config.toml`، `interval_hours = 24` و `[telegram] enabled = true` است. توکن واقعی را در مخزن عمومی ذخیره نکنید.

### رفتار انتشار

- اولین بررسی هنگام اجرای worker انجام می‌شود؛ سپس هر ۲۴ ساعت یک نوبت بررسی و انتشار.
- در هر نوبت ابتدا یک جمع‌بندی کوتاه منتشر می‌شود؛ سپس برای هر کالا یک پیام مستقل شامل عکس و کپشن نام، لینک خرید، قیمت، درصد تخفیف و وضعیت اطمینان می‌آید. برای هر دسته ابتدا عنوان دسته و سپس تا ۵ پیام کالا ارسال می‌شود؛ تعداد کل به دسته‌های موجود بستگی دارد. پیام‌های کالا بدون اعلان صوتی اضافه‌اند. اگر عکس موجود نباشد یا تلگرام صریحاً آن را رد کند، مشخصات همان کالا در یک پیام متنی مستقل می‌آید.
- حتی اگر قیمت‌ها تغییر نکرده باشند، نوبت بعدی گزارش جدید خود را منتشر می‌کند.
- اگر پیشنهاد معتبر نداریم، پست صریحاً همین نتیجه را اعلام می‌کند.
- اگر دریافت تمام داده شکست بخورد، پست «دریافت داده ناموفق بود» منتشر می‌شود؛ این حالت با نبود تخفیف معتبر متفاوت است.
- ارسال موفق با شناسهٔ پیام در SQLite ثبت می‌شود. ارسال مجدد همان بازهٔ زمانی بعد از restart حذف می‌شود؛ جدول قبلی اعلان‌های کالایی دیگر در انتشار دخالت ندارد.
- محدودیت متن تلگرام رعایت می‌شود: قالب نمونه با ۲۰ کالا در یک پست جا می‌گیرد. اگر متن بیشتر شود، تعدادی از پیشنهادها به گزارش کامل ارجاع داده می‌شوند.
- برای پاسخ 429 تلگرام تا سه تلاش با تأخیر محدود انجام می‌شود. برای timeout مبهم، retry فوری انجام نمی‌شود؛ چون ممکن است تلگرام پیام را دریافت کرده باشد. Bot API تضمین exactly-once ندارد؛ پس بعد از شکست مبهم و restart، احتمال پیام تکراری کاملاً قابل حذف نیست.
- فاصله از شروع بررسی قبلی محاسبه می‌شود؛ برای ساعت ثابتِ تقویمی مثل ۰۰/۰۶/۱۲/۱۸ طراحی نشده است. برای هر نصب یک worker اجرا کنید.

برای افزودن لینک گزارش کامل به انتهای پست، در بخش `[telegram]` بنویسید:

```toml
report_url = "https://your-site.example/deals/"
```

این گزینه خودبه‌خود سایت را میزبانی نمی‌کند؛ آدرس باید گزارش واقعاً منتشرشده باشد.

### پیش‌نمایش بدون ارسال

```bash

```

این دستور داده‌های واقعی پیکربندی‌شده را بررسی می‌کند و فایل `output/channel-post.html` می‌سازد؛ هیچ پیامی ارسال نمی‌کند. برای پیش‌نمایش ساختگی و بدون شبکه:


فایل `demo-output/channel-post.html` را باز کنید. حالت demo با برچسب مشخص، هیچ‌گاه به کانال پیام نمی‌فرستد.

توکن را در کد، feed یا فایل عمومی نگذارید. فایل `.env` در gitignore قرار دارد؛ برای Docker از `.env.example` کپی بگیرید. این ربات منتشرکنندهٔ کانال است؛ منوی گفت‌وگویی، دریافت دستورات از اعضا یا webhook نیاز ندارد.

## انتشار خودکار کانال با GitHub Actions

برای این روش سرور شخصی لازم نیست. فایل‌های داخل پوشهٔ پروژه را در ریشهٔ مخزن `real-deal-radar` روی شاخهٔ پیش‌فرض قرار دهید؛ پوشهٔ مخفی `.github` هم باید آپلود شود. بارگذاری خود فایل ZIP باعث اجرا نمی‌شود.

1. در BotFather ربات بسازید و آن را با مجوز **Post Messages** مدیر کانال کنید.
2. در مخزن به **Settings → Secrets and variables → Actions → New repository secret** بروید و `TELEGRAM_BOT_TOKEN` و `TELEGRAM_CHAT_ID` را ثبت کنید. شناسهٔ کانال عمومی مانند `@your_channel` یا شناسهٔ عددی کانال خصوصی است.
3. دریافت مستقیم دیجی‌کالا و کشف بازار از ترب در تنظیمات پیش‌فرض فعال است. در صورت داشتن منبع اختصاصی، Secret اختیاری `MARKET_FEED_URL` (جایگزین ترب) یا `CANDIDATE_FEED_URL` (جایگزین دیجی‌کالا) را مطابق قالب JSON نمونه تنظیم کنید. فایل نمونه دادهٔ ساختگی است و برای انتشار واقعی مناسب نیست.
4. در **Actions → Telegram channel report → Run workflow**، پیش‌فرض **Preview only** خاموش است و هر اجرای دستی یک پست به کانال می‌فرستد، حتی اگر در همان بازهٔ شش‌ساعته قبلاً پست منتشر شده باشد. برای بررسی بدون ارسال، این گزینه را روشن کنید؛ فایل گزارش در Artifacts همان اجرا قابل دریافت است. اجرای دوباره با Run workflow یا Re-run یک نوبت دستی جدید محسوب می‌شود.
5. اجرای زمان‌بندی‌شده پس از قرار گرفتن workflow روی شاخهٔ پیش‌فرض، با Actions فعال، هر ۲۴ ساعت انجام می‌شود. پیش‌نمایش دستی زمان‌بندی را متوقف نمی‌کند؛ تنظیم منابع و Secrets را پیش از فعال کردن Actions کامل کنید.

زمان‌ها با cron برابر `17 12 * * *` تنظیم شده‌اند؛ در تهران حدود ۱۵:۴۷ روزانه. زمان اجرا تضمین دقیق ندارد و ممکن است عقب بیفتد یا حذف شود. در مخزن عمومی بدون فعالیت، GitHub ممکن است پس از ۶۰ روز زمان‌بندی را غیرفعال کند. مرجع: [GitHub scheduled workflows](https://docs.github.com/en/actions/reference/workflows-and-actions/events-that-trigger-workflows#schedule).

برای تغییر فاصله، هم `interval_hours` در `config.toml` و هم cron در `.github/workflows/channel.yml` را تغییر دهید؛ برای ۳ ساعت، `interval_hours = 3` و `17 */3 * * *`. cron برای فاصله‌های دلخواه اعشاری مناسب نیست؛ worker محلی از آن‌ها پشتیبانی می‌کند.

تاریخچهٔ قیمت و ارسال با GitHub Cache بین اجراها منتقل می‌شود؛ حذف یا انقضای cache تاریخچه را از دسترس خارج می‌کند، پس ذخیره‌سازی دائمی تضمین نمی‌شود. اجراهای این workflow هم‌زمان نمی‌شوند. اجرای خودکار یک پست در هر بازهٔ UTC ارسال می‌کند و کمی تأخیر اجرای قبلی باعث حذف بازهٔ بعدی نمی‌شود. اجرای دستی مستقل است و سهمیهٔ نوبت خودکار را مصرف نمی‌کند. وضعیت ارسال (`sent`، `skipped`، `failed`، `preview`) در `latest.json` و لاگ اجرا ثبت می‌شود. در هر دسته حداکثر ۵ کالا معرفی می‌شود: موارد دارای شواهد بازار با ✅ و باقی موارد موجود و غیرسوپرمارکتی با تخفیف اعلامی دیجی‌کالا با ⚠️. موارد ⚠️ نام و لینک، قیمت فعلی و درصد تخفیف دارند و صریحاً «کمترین قیمت بازار تأیید نشده» معرفی می‌شوند. کالای منقضی، ناموجود یا زیر حد تخفیف وارد این فهرست نمی‌شود.

هر مخزن/نصب یک کانال و تنظیم مستقل دارد. کاربران می‌توانند مخزن را Fork کنند و Secrets خودشان را تنظیم کنند. این بسته ربات چندکاربره با فرمان‌های تلگرامی نیست.

## توسعه و آزمون

```bash
python -m unittest discover -s tests -v
```

آزمون‌ها پوشش می‌دهند: مقایسه با پایین‌ترین قیمت، جلوگیری از شاهد تکراری، نسخه/گارانتی، شواهد قدیمی/آینده/منقضی، ارسال، دادهٔ نامعتبر، ذخیرهٔ تاریخچه، تغییر زمان‌بندی بدون restart، تبدیل ریال، SKU دقیق، تولید گزارش و escape HTML، و تولید یک پست کانالی، محدودیت متن، جلوگیری از انتشار تکراری پس از restart، خطای نرخ و شکست ارسال. تست CI برای Python 3.11، 3.12 و 3.13 آماده است.

محدودیت فعلی: یک worker برای هر فایل پایگاه داده اجرا کنید؛ چند پردازش هم‌زمان برای یک نصب پشتیبانی نمی‌شود. در روش worker، عمر برنامه به روشن بودن دستگاه/سرور بستگی دارد. ابزار دارای retry محدود و timeout است؛ دریافت ناموفق در گزارش پنهان نمی‌شود. worker به سرور یا دستگاه همیشه روشن نیاز دارد؛ روش GitHub Actions روی runner گیتهاب اجرا می‌شود. در هر دو روش اتصال قابل دسترس به Telegram Bot API لازم است.

نسخهٔ 0.4.1: انتخاب نامزدها بین دسته‌ها تقسیم می‌شود و مدل‌های دارای شناسهٔ قابل‌تطبیق اولویت دارند؛ بنابراین اولین کالاهای یک دسته کل سهمیه را مصرف نمی‌کنند. علت‌های شکست جست‌وجو و تطبیق در لاگ Actions به‌صورت شمارش‌های فاقد مقادیر Secrets ثبت می‌شوند. این تغییر تضمین یافتن ۲۰ پیشنهاد معتبر نیست.

نسخهٔ 0.4.2: فیلد `installment.providers` ترب گزینهٔ پرداخت اقساطی است و دیگر باعث حذف فروشندهٔ نقدی نمی‌شود. مبلغ مورد مقایسه همچنان از Offer واقعی فروشگاه خوانده می‌شود؛ مبلغ قسط به جای قیمت کالا استفاده نمی‌شود. ردیف‌های تکراری یک فروشگاه پیش از تخصیص سهمیه حذف می‌شوند.

نسخهٔ 0.4.3: اجرای دستی مستقل از زمان‌بندی شش‌ساعته پیام می‌فرستد و پیش‌نمایش دستی اختیاری است. رنگ‌های معادل فارسی/انگلیسی و نگارش متفاوت گارانتی همسان می‌شوند، ولی مدت و شرکت گارانتی حذف نمی‌شوند. یک بلوک JSON-LD خراب، بلوک معتبر محصول را از بین نمی‌برد. تمام جست‌وجوهای ترب فاصله دارند؛ پاسخ‌های 403، 429 و 490 بررسی ترب را در همان نوبت متوقف می‌کنند و وضعیت قطع دسترسی صریحاً گزارش می‌شود. رفع خطای دسترسی خارجی یا پیدا شدن پیشنهاد تأییدشده تضمین نشده است. برای اجرای قابل اتکا با دادهٔ قراردادی، `MARKET_FEED_URL` باید به feed واقعی و مجاز مطابق قالب نمونه متصل شود؛ نمونه‌ها شاهد واقعی نیستند.

نسخهٔ 0.4.4: نبود شواهد بازار دیگر مانع نمایش کالاها نیست. `deals` فقط پیشنهادهای دارای شواهد بازار را نگه می‌دارد؛ `advertised_offers` فهرست جداگانهٔ تخفیف‌های اعلامی و تأییدنشده است. ابتدا پیشنهادهای تأییدشده و سپس بالاترین درصدهای تخفیف اعلامی تا سقف `max_items` نمایش داده می‌شوند. پیام تلگرام، گزارش HTML و Markdown نام، لینک، قیمت و درصد تخفیف را همراه با برچسب اطمینان نشان می‌دهند. درصد اعلامی به معنای صرفه‌جویی واقعی در بازار نیست.

نسخهٔ 0.4.5: تصویر اصلی JPG/PNG کالا از `images.main.url` دیجی‌کالا دریافت و در `image_url` ذخیره می‌شود. ارسال عکس با تنظیم `telegram.photos_enabled = true` به‌صورت پیش‌فرض فعال است. پس از گزارش متنی، عکس‌ها با `sendMediaGroup` در دسته‌های حداکثر ۱۰تایی ارسال می‌شوند؛ عکس تک‌مانده با `sendPhoto` می‌رود. هر عکس کپشن و لینک همان کالا را دارد. نبود عکس یا شکست ارسال عکس، گزارش متنی موفق را از بین نمی‌برد؛ نتیجه در `telegram_photos` در فایل JSON و لاگ ثبت می‌شود. در رد صریح آلبوم با HTTP 400، عکس‌ها جداگانه امتحان می‌شوند تا یک لینک خراب بقیهٔ عکس‌ها را حذف نکند؛ پس از timeout هیچ ارسال کور تکرار نمی‌شود. عکس‌ها از URL عمومی به تلگرام سپرده می‌شوند و نمایششان به دسترسی تلگرام به CDN دیجی‌کالا وابسته است.

نسخهٔ 0.4.6: خروجی فعلی یک جمع‌بندی کوتاه و پیام مستقل عکس+متن برای هر کالا است؛ آلبوم نسخهٔ قبل حذف شده است. زمان‌بندی پیش‌فرض در config و GitHub Actions هر ۱۲ ساعت است (حدود ۰۳:۴۷ و ۱۵:۴۷ تهران). اجرای دستی مستقل ادامه دارد. میان پیام‌های کالا ۳٫۱ ثانیه فاصله قرار می‌گیرد و پاسخ نرخ 429 رعایت می‌شود.

نسخهٔ 0.5.0: هر نوبت ۱۲ساعته دو بخش دارد: تا ۲۰ کالای پرتخفیف و تا ۲۰ کالای پرفروش، هر بخش با جمع‌بندی و پیام عکس+متن مستقل برای هر کالا. پرفروش‌ها از `/v1/best-selling/` دریافت می‌شوند. این مسیر سراسری فقط ۵۰ کالا دارد و صفحه‌بندی را نادیده می‌گیرد؛ ابتدا موارد موجود و غیرسوپرمارکتی همین فهرست انتخاب می‌شوند، سپس ظرفیت باقی‌مانده از پرفروش‌های دسته‌های تنظیم‌شده با `category_id` پر می‌شود. جایگاه و نام فهرست مبدأ در کپشن و JSON ذخیره می‌شود؛ رتبهٔ دسته به عنوان رتبهٔ سراسری معرفی نمی‌شود و تعداد فروش واقعی در دسترس نیست. کالاهای پرفروش لازم نیست تخفیف داشته باشند؛ درصد صفر هم معتبر است.

بخش `[bestsellers]` با `enabled = true` و `max_items = 20` فعال است. `category_codes` دسته‌های تکمیل‌کننده را تعیین می‌کند. در صورت قطع منبع، تنها دادهٔ واقعاً دریافت‌شده منتشر می‌شود؛ هیچ فهرست ساختگی برای رساندن تعداد به ۲۰ تولید نمی‌شود. تعداد پیام‌ها برای دو فهرست کامل، ۲ جمع‌بندی و ۴۰ پیام کالا است. ممکن است یک کالا هم پرفروش باشد و هم پرتخفیف و در هر دو بخش دیده شود.

نسخهٔ 0.6.0: پیش‌فرض اجرا هر ۲۴ ساعت، حدود ۱۵:۴۷ تهران است. `[grouping] enabled = true` و `items_per_category = 5` هر دو بخش تخفیف و پرفروش را بر اساس گروه اصلی نوع کالا (مثلاً کالای دیجیتال، خانه و آشپزخانه، مد و پوشاک) تفکیک می‌کنند. سقف کلی ۲۰ کالا در این حالت اعمال نمی‌شود. گروه‌های خالی نمایش داده نمی‌شوند و گروه دارای کمتر از ۵ مورد با همان تعداد واقعی منتشر می‌شود.

تخفیف‌ها با درصد تخفیف اعلامی نزولی انتخاب می‌شوند و برچسب تأیید بازار مستقل باقی می‌ماند. پرفروش‌ها با جایگاه منبع انتخاب می‌شوند؛ جایگاه دسته و سراسری به‌هم تبدیل نمی‌شوند. فهرست‌های تکمیل‌کنندهٔ پرفروش پیش از برش گروه‌ها کامل خوانده می‌شوند، تا دستهٔ اول سهم بقیه را مصرف نکند. دادهٔ دسته در `discount_groups` و `bestseller_groups`، پیام‌های کانال و گزارش HTML/Markdown ثبت می‌شود. اجرای دستی همچنان مستقل از زمان‌بندی است. سقف `max_items` قبلی فقط در حالت خاموش بودن grouping اعمال می‌شود.


نسخهٔ 0.7.0: اتصال پیش‌فرض بررسی قیمت، MCP ترب از مخزن خود پروژه است (`torob.backend = "mcp"`). کد MIT و lockfile در `vendor/torob-mcp` قرار دارند؛ نسخه در هر اجرا از اینترنت جایگزین نمی‌شود. در اجرای محلی، پیش از شروع ربات، Node.js 24 نصب و فرمان‌های زیر اجرا شوند:

```sh
npm ci --ignore-scripts --prefix vendor/torob-mcp
npm run build --prefix vendor/torob-mcp
```

GitHub Actions این دو مرحله را خودکار انجام می‌دهد. Dockerfile نیز مرحلهٔ ساخت MCP و runtime Node را دارد. برای مسیر جداگانهٔ سرور محلی، `TOROB_MCP_ENTRY` را به فایل `dist/stdio.js` تنظیم کنید. توکن تلگرام و secrets ربات به پردازش MCP داده نمی‌شوند.

در هر دستهٔ دقیق نوع کالا (`grouping.category_level = "type"`) تا ۵ انتخاب منتشر می‌شود. در بخش تخفیف، مقایسه‌های همسان ابتدا با سطح اطمینان و سپس صرفه‌جویی نسبت به کمترین پیشنهاد همسان مشاهده‌شده مرتب می‌شوند؛ درصد اعلامی برای موارد بدون شاهد، فقط معیار جایگزین است. کالاهایی که در دادهٔ قابل‌مقایسه گران‌تر یا مساوی ترب هستند، از بخش تخفیف انتخاب نمی‌شوند؛ در بخش پرفروش رتبهٔ منبع حفظ می‌شود و گران‌تر بودن در کپشن قابل مشاهده است.

رنگ اطمینان مربوط به مقایسهٔ ترب است: 🟢 حداقل ۳ فروشگاه متمایز با مدل، ظرفیت/نسخه، رنگ، سایز و گارانتی همسان و موجودی صریح و وضعیت نو؛ 🟡 کمتر از این تعداد یا اطلاعات همسان ناقص؛ ⚪ منبع دریافت نشده یا مدل همسان پیدا نشده است. موجودی نامعلوم، آگهی، قیمت نامعتبر، کالای کارکرده و هشدار خرید وارد قیمت قابل‌مقایسه نمی‌شوند. امتیاز فروشگاه امتیاز محصول نیست. برچسب سبز، تأیید مستقل صفحهٔ فروشگاه یا تضمین ارزان‌ترین بودن در کل بازار نیست؛ وضعیت قدیمی `deals/verified` همچنان فقط مسیر تأیید مستقل قبلی است.

کپشن شامل دلیل انتخاب، قیمت دیجی‌کالا، درصد اعلامی، بازهٔ پیشنهادهای همسان ترب، اختلاف مبلغی و درصدی، تعداد فروشگاه، زمان دریافت و لینک ترب است. ارسال در مقایسهٔ ترب محاسبه نشده است. `loaded_list_complete` و `truncated` ثبت و پوشش محدود نمایش داده می‌شود؛ خروجی ابزار حداکثر ۵۰ پیشنهاد دارد. `fetched_at` زمان دریافت داده است، نه زمان آخرین تغییر قیمت فروشنده. MCP تاریخچهٔ قیمت یا نقد خریداران ارائه نمی‌کند.

برای بررسی واقعی دسترسی از میزبان GitHub، workflow «Torob MCP live check» و `python scripts/check_torob_mcp.py` اضافه شده‌اند. این بررسی جست‌وجو، جزئیات و ابزار فروشندگان را می‌خواند؛ هیچ پیامی در تلگرام نمی‌فرستد. خطای منبع در گزارش JSON همان اجرا دیده می‌شود. زمان‌بندی کانال همچنان هر ۲۴ ساعت و اجرای دستی مستقل است.

در حالت زرد با مشخصات ناقص، دامنهٔ قیمت‌های فهرست ترب با عبارت «نسخهٔ همسان تأیید نشده» نمایش داده می‌شود؛ از این قیمت‌ها اختلاف یا صرفه‌جویی محاسبه نمی‌شود. چند فهرست ترب برای یک مدل می‌توانند بررسی شوند، اما فروشگاه تکراری در سطح اطمینان دوباره شمرده نمی‌شود.


نسخهٔ 0.8.0 — ویترین روزانهٔ کم‌حجم: تنظیم پیش‌فرض `[showcase] enabled = true` است. در کل گزارش تا ۲۵ کالای متفاوت انتخاب می‌شود: حداکثر ۱۵ تخفیف ارزشمند و ۱۰ پرفروش منتخب، با سقف مشترک ۲ کالا از هر نوع در هر دو بخش. پیام جداگانهٔ عنوان دسته و بخش حذف شده است؛ خروجی یک جمع‌بندی کوتاه و تا ۲۵ پیام عکس‌دار با کپشن چهارخطی است. فایل گزارش کامل همچنان جزئیات شواهد و مقایسه را دارد. اگر تنوع یا دادهٔ کافی موجود نباشد، تعداد کمتر می‌شود و سهمیه با کالای نامعتبر پر نمی‌شود.

کالای مشترک دو بخش فقط یک بار معرفی می‌شود. جدول `showcase_items` در تاریخچهٔ هر کانال، فقط پس از تأیید ارسال عکس یا متن جایگزین به‌روزرسانی می‌شود. کالای قبلاً ارسال‌شده تنها با تغییر حداقل `showcase.price_change_percent = 5` درصد در قیمت دیجی‌کالا، نسبت به آخرین قیمت ارسال‌شدهٔ همان نسخه/گارانتی، دوباره واجد شرایط می‌شود. این محدودیت در اجرای دستی هم اعمال می‌شود؛ اجرای دستیِ دوباره می‌تواند فقط جمع‌بندی داشته باشد. پیش‌نمایش و ارسال ناموفق، کالا را ارسال‌شده علامت نمی‌زنند. حذف cache این سابقه را نیز حذف می‌کند.

`showcase.max_items`، `discount_items`، `bestseller_items`، `max_per_type` و `price_change_percent` قابل تنظیم‌اند. در حالت ویترین، سقف کلی قبلی و پیام‌های حالت گروه‌بندی اعمال نمی‌شوند. زمان‌بندی هر ۲۴ ساعت حفظ می‌شود.
